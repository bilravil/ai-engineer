Контекстный слой: от источников до запроса к модели

23 нояб. 2026 г.время чтения ~8 мин.

← Context Engineering · Краткий справочник

Коротко

Prompt engineering задаёт, как сформулирована задача и требования к ответу. Context engineering отвечает за весь доступный модели набор информации в ходе работы приложения. Контекстный слой собирает нужные сведения из источников, проверяет допустимость, отбирает и оформляет их. MCP может стандартизировать подключение источников и инструментов, но не заменяет правила отбора и доступа.

Охваченные понятия

Context vs Prompt Engineering

Prompt engineering включает не только одну фразу: инструкции, примеры, ограничения и формат тоже относятся к работе с промптом. Context engineering рассматривает более широкий процесс: что получит модель, откуда, в какой форме и на каком шаге. Если ответ требует действующего правила продукта, улучшение формулировки не заменит отсутствующий документ. Такое расширение от инструкции к набору доступных сведений описано в материале Anthropic.

What is a Context Layer?

Контекстный слой — архитектурная роль, отвечающая за подготовку информации для модели. Это не специальный слой нейросети и не обязательный отдельный сервер. Его можно реализовать кодом приложения, поисковым конвейером и хранилищем состояния либо распределить между несколькими компонентами. Название описывает ответственность, а не единственный стандарт реализации.

Context Sources

Источники контекста — документы, базы, репозитории, переписка, API, результаты инструментов и других агентов. Источник доступных сведений не обязательно является надёжным основанием для любого вывода: старое обращение клиента не равно действующему правилу продукта, а код реализации не всегда совпадает с обещанным поведением.

MCP

Model Context Protocol — открытый протокол обмена между AI-приложением и внешними возможностями. В архитектуре есть host — приложение, client — его компонент взаимодействия, и server — программа, предоставляющая возможности. Серверы могут предоставлять tools, resources и prompts; поддержка конкретных возможностей зависит от участников. Протокол не предписывает приложению, как управлять контекстом — см. официальную архитектуру MCP.

Суть своими словами

Представь помощника поддержки. Промпт говорит: «Объясни порядок восстановления доступа». Но ответ зависит от продукта, способа входа и текущей инструкции. Контекстный слой находит эти сведения и передаёт их модели. MCP — один из способов получить их через единый интерфейс; он не решает за приложение, какие документы нужны и кому их разрешено читать.

Как работает

Вход, выход и компоненты

Вход: вопрос, идентичность пользователя, разрешённая задача, исходные источники и текущая история. Выход: компактный контекст с источниками, версиями и существенными условиями, а также доступные для этого шага инструменты.

Полезно отдельно учитывать происхождение и актуальность каждого фрагмента. Это не требует одной универсальной схемы: для учебного приложения достаточно явно хранить текст, ID документа, версию и область доступа.

Подготовка контекста по шагам

  1. Понять задачу. Какие факты нужны для ответа? В нашем примере — способ входа и действующее правило восстановления, а не вся история аккаунта.
  2. Определить область доступа. Серверная часть устанавливает пользователя и организацию; не принимает написанное моделью значение организации как доказательство права.
  3. Выбрать источники. Инструкция даёт порядок действий, база — текущий режим входа, переписка — симптомы. У каждого источника своя роль.
  4. Получить сведения. Напрямую через API или через подключённый MCP-сервер. Если модель выбирает инструмент, приложение выполняет вызов и возвращает результат.
  5. Нормализовать. Привести разные форматы к понятным полям, сохранить единицы, время и версию. Нормализация не должна уничтожить исключение или скрыть противоречие.
  6. Отобрать. Удалить дубли, старые версии и не относящееся к вопросу, соблюсти права и бюджет. Самый похожий по словам фрагмент не обязательно правильный.
  7. Собрать запрос. Разделить инструкции, факты из базы и цитируемые документы, обозначить источники. Включить правило действий при нехватке данных.
  8. Проверить и обновить состояние. Сопоставить ответ с материалами; для следующего шага сохранить нужное состояние, а не рассчитывать на бесконечную память модели.

Где здесь MCP

Упрощённый путь: приложение-host → компонент-client → MCP-server → нужный источник. Сервер оборачивает доступные операции, приложение решает, как использовать их результат. Саму LLM не следует отождествлять с MCP-клиентом: это разные компоненты системы.

Поддержка MCP снижает потребность проектировать отдельный интерфейс общения для каждой пары участников, но остаются разработка подключения к исходной системе, авторизация и проверка доступных возможностей. «Совместимый клиент» не означает, что любые сервер и клиент автоматически выполнят любую задачу без настройки.

Развёрнутый пример: помощник поддержки Portal

Учебный сквозной сценарий; продукт, документы и ответы инструментов вымышлены. Продолжение разбирается в безопасности и оценке.

Вопрос оператора организации A: «Клиент не получает письмо для входа. Как восстановить доступ?»

Доступные источники:

  • D1: актуальная инструкция Portal — «Для обычного входа проверить спам и адрес; срок ссылки — 15 минут».
  • D2: актуальное исключение — «При SSO входом управляет организация; для восстановления обратиться к её администратору».
  • D0: старая версия инструкции со сроком 60 минут.
  • База аккаунтов: для нужного клиента в A указан login_method = sso.
  • Старые обращения поддержки: похожие письма, не утверждённые правила.

Шаги:

  1. Prompt engineering: задаём инструкцию «Сформулируй порядок действий по источникам, укажи применимое исключение; если режим входа неизвестен, уточни его».
  2. Context sources: выбираем базу аккаунтов для режима входа, D1 и D2 для правил. Одно старое обращение не подменяет их.
  3. MCP: в учебной архитектуре host вызывает через client инструмент get_login_method MCP-сервера. Сервер проверяет доступ и возвращает только нужный статус. Название инструмента придумано; готовый сервер не запускался.
  4. Context layer: подбирает D1 и D2, отклоняет D0 как старую версию, сохраняет факт sso, отделяет симптомы клиента от правил.
  5. Передаёт модели инструкции, вопрос, режим входа и два помеченных документа. Секреты и полный профиль клиента не нужны.
  6. Ожидаемый ответ: «Для этого клиента используется SSO: восстановлением управляет администратор организации [D2]. Обычная процедура с письмом из D1 не является основным путём для этого режима».
  7. Проверка: ответ учёл режим входа, сослался на исключение, не выдумал действие «я отправил письмо» и не использовал срок из D0.

Вариант сбоя: инструмент базы недоступен, но приложение молча подставляет password вместо неизвестного значения. Модель даёт неправильный порядок действий даже при хороших документах. Исправление — явно вернуть отсутствие факта и запросить режим входа; сбой получения данных не превращать в факт.

Практические сценарии из жизни

Это типовые рабочие ситуации, не подтверждённые внедрения конкретных компаний.

Ответы поддержки по нескольким продуктам. Оператору нужен ответ по текущей версии и конкретному режиму аккаунта. Подключают документы и разрешённые данные аккаунта, фильтруют по продукту и организации. Проверяют применение исключений и происхождение каждого факта. Полезность достигается согласованием источников, а не максимальным количеством текста.

Помощник разработчика в репозитории. Задача касается одного API. Нужны код текущей ветки, контракт и результаты проверок; обсуждение из старой задачи может быть полезной подсказкой, но не основанием игнорировать действующий контракт. Оценивают, какие версии использованы и объясняет ли ответ реальные файлы. MCP может подключать инструмент, но сам по себе не выбирает правильную ветку.

Ограничения и типичные ошибки

Ограничения

  • Источники обновляются с разной частотой. Свежий статус базы и устаревшая инструкция могут давать конфликт; нужно хранить время и версию и иметь правило разрешения противоречий.
  • Нормализация упрощает сравнение, но может убрать смысл. Если SSO-исключение превратилось в общую фразу «обратиться в поддержку», модель теряет точный следующий шаг.
  • MCP стандартизирует обмен, а не достоверность содержимого. Полученный через корректный протокол текст может быть старым, нерелевантным или недоверенным.

Когда выбрать другой подход

Если источником служит один короткий неизменный текст, может хватить прямой передачи в промпт. Для одной простой интеграции обычный API-вызов может быть достаточен; необходимость MCP зависит от архитектуры. Отдельный платформенный продукт не обязателен для выполнения роли контекстного слоя.

Самостоятельная практика

Составь таблицу источников для собственного проекта: какие факты нужны, откуда они берутся, как часто меняются и кому доступны. На бумаге собери контекст для вопроса оператора из примера. Затем убери факт о режиме входа. Критерий успеха — можешь объяснить, что теперь нужно уточнить, и почему изменение инструкции не восстановит отсутствующий факт. Подключать реальный MCP-сервер для этого упражнения не требуется.

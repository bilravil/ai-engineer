## Коротко

Structured output нужен, когда результат должна обработать программа. Function calling позволяет модели предложить вызов именованной операции с аргументами; исполняет её приложение или предусмотренная провайдером среда. Оба механизма используют структуру, но у них разные назначения: данные для следующего шага и запрос на действие. Корректная структура не гарантирует правильности значений или права выполнить операцию.

## Охваченные понятия

### Structured Outputs

В широком смысле это ответы заданного формата: JSON, XML, таблица или другой контракт. Нужно различать просьбу в промпте «ответь JSON» и специальный режим API с ограничением генерации по поддерживаемой схеме. Первый направляет модель, второй может обеспечивать соответствие форме в рамках своего контракта; всё равно нужно обрабатывать отказ, обрыв и иные неуспешные исходы.

Схема задаёт типы, обязательные поля и допустимые значения. Она не доказывает, что срок, категория или источник выбраны верно. О механизме ограниченной генерации — [документация structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

### Function Calling

Модель получает описание функции и структуру аргументов, затем может вернуть запрос на её вызов. Для обычного клиентского инструмента приложение проверяет запрос, выполняет код и возвращает результат модели. Вызов в ответе модели не означает, что код уже выполнился. Некоторые инструменты исполняются на стороне провайдера; конкретный контракт нужно различать — см. [описание tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works).

## Суть своими словами

Если нужен объект для маршрутизации обращения, модель может вернуть структурированные данные. Если нужно узнать режим входа, нужен вызов инструмента. Приложение не должно угадывать намерение по фразе «я бы проверил аккаунт» и не должно исполнять всё, что удалось разобрать как JSON.

## Как работает

### Контракт ответа

1. Определяют поля и их смысл: какие значения допустимы, что означает отсутствие факта.
2. Описывают поддерживаемую схему либо явно заданный текстовый формат.
3. Получают завершённый ответ и проверяют его статус.
4. Разбирают и валидируют структуру.
5. Проверяют значения по задаче: существуют ли указанные источники, применимо ли правило, не выдуман ли факт.
6. Только после этого передают результат следующему компоненту.

### Цикл инструмента

`описание функции → запрос модели на вызов → проверка аргументов и доступа → выполнение → результат инструмента → следующий запрос к модели`.

Идентичность пользователя и область организации берутся из доверенного состояния приложения, а не из свободно выбранного моделью поля. Успешная схема аргументов означает лишь, что они имеют допустимую форму. Ошибки инструмента нужно возвращать явно; их нельзя превращать в выдуманный успешный результат.

## Развёрнутый пример: восстановление доступа

Учебный сценарий Portal; инструменты не запускались, JSON ниже — образцы ожидаемых данных.

**Вопрос:** «Клиент client_42 не получает письмо для входа. К кому направить?» Режим входа пока неизвестен.

### Шаг 1. Получение факта через функцию

Приложение описывает read-only инструмент `get_login_method` с обязательным строковым аргументом `account_id`. Это придуманное имя, не стандартная функция API.

Ожидаемый запрос на вызов, показанный как упрощённая запись:

```json
{"name":"get_login_method","arguments":{"account_id":"client_42"}}
```

Сервер проверяет право оператора читать нужный аккаунт. При разрешённом доступе условно возвращает:

```json
{"account_id":"client_42","login_method":"sso","status":"ok"}
```

Это **function calling**: запрос на операцию, проверка, исполнение и наблюдение. Пока результат не получен, утверждать, что аккаунт проверен, нельзя.

### Шаг 2. Формат итогового результата

После получения факта и документа D2 про SSO нужен объект для интерфейса оператора. Учебная схема:

```json
{
  "type":"object",
  "properties":{
    "status":{"type":"string","enum":["answer","clarify"]},
    "next_step":{"type":["string","null"]},
    "source_ids":{"type":"array","items":{"type":"string"}}
  },
  "required":["status","next_step","source_ids"],
  "additionalProperties":false
}
```

Это логическая JSON Schema для объяснения. Поддержку её конструкций и способ передачи нужно проверить для конкретного API; пример не является готовой конфигурацией SDK.

Ожидаемый объект:

```json
{
  "status":"answer",
  "next_step":"Направить к администратору организации для восстановления SSO-доступа",
  "source_ids":["D2"]
}
```

Это **structured output** для интерфейса, а не ещё один выполненный инструмент.

### Шаг 3. Проверки результата

- Все обязательные поля присутствуют, типы и значения `status` допустимы.
- D2 действительно был предоставлен и содержит применимое правило.
- Для SSO выбран администратор организации, а не обычная отправка письма.
- Объект не утверждает, что восстановление уже выполнено.

**Вариант сбоя:** объект полностью соответствует схеме, но `next_step` предлагает обычный сброс пароля. Структура верна, смысл неверен. Исправление — проверить использование режима SSO и исключения D2, а не только повторно парсить JSON.

Если инструмент вернул ошибку доступа, корректный путь — обработать её по правилам приложения. Нельзя заменять неизвестный режим на `password`; бизнес-правила также должны определять, как выдавать `clarify` и что писать в `next_step`. Приведённая схема сама не связывает логически все поля.

## Практические сценарии из жизни

Типовые рабочие ситуации, не подтверждённые кейсы конкретных организаций.

**Разбор письма в карточку обращения.** Приложению нужны категория, краткое содержание и отсутствующие сведения. Схема уменьшает нестабильность формы, а проверка по исходному письму выявляет выдуманные поля. Критерий — пригодность данных для системы, а не только корректный синтаксис.

**Получение статуса заказа или аккаунта.** Нужен актуальный факт из базы. Функция позволяет описать операцию явно; приложение проверяет права и возвращает результат. Для операций с изменением состояния дополнительно нужны меры от повторного исполнения и проверки намерения пользователя. Критерий — соответствие отчёта фактическому результату операции.

## Ограничения и типичные ошибки

### Ограничения

- Схема не удостоверяет истинность значений. Поле с существующим типом может содержать неверное правило или ID.
- Поддерживаются не все конструкции схем и не все режимы у каждой модели. Формат запроса проверяют по документации, а не копируют по похожему названию функции.
- Отказы, остановка по лимиту и сетевые сбои требуют отдельных ветвей. Даже поддерживаемый строгий режим нельзя трактовать как «любой ответ всегда готов к обработке».

### Ошибки применения

| Ошибка | Проявление и причина | Исправление |
| --- | --- | --- |
| Приравнять «ответь JSON» к строгому контракту | Приходит текст вокруг объекта или пропущенное поле | Использовать подходящий режим и валидацию |
| Считать вызов модели выполненной функцией | Пользователю сообщён несуществующий результат | Дождаться исполнения и проверить итог |
| Доверять аргументу организации из модели | Запрос читает чужие данные | Определять и проверять доступ на сервере |
| Выдумывать значение для обязательного поля | Валидный объект содержит ложный факт | Разрешить неизвестное и определить ветвь уточнения |
| Проверять только JSON | Схема соблюдена, действие не подходит | Проверять источники и бизнес-условия |

### Когда выбрать другой подход

Если поле можно точно извлечь обычным парсером, модель может не понадобиться. Если функция всегда одна и её аргументы уже известны приложению, необязательно поручать выбор вызова LLM. Для свободного черновика редактору жёсткая схема может быть лишней.

## Самостоятельная практика

Проверь три объекта: корректный, без `source_ids`, с допустимой формой и неправильным действием для SSO. Объясни, какой сбой найдёт схема, а какой — только проверка смысла. Затем смоделируй отказ инструмента в доступе. Критерий успеха — приложение не выдаёт непроверенный объект и не сообщает о невыполненной операции.

## Проверка понимания

- [ ] Различаю формат ответа и запрос на вызов функции.
- [ ] Могу отделить проверку структуры от проверки смысла.
- [ ] Знаю, кто выполняет клиентский инструмент и проверяет доступ.
- [ ] Могу обработать неизвестное значение и ошибку инструмента.

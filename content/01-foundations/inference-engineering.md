## Коротко

Инференс — применение модели; inference engineering — организация его выполнения с нужными задержкой, пропускной способностью, стоимостью и доступностью. Она включает вычисления на GPU и управление памятью, сервер обработки запросов, масштабирование и наблюдение за работой. Эту тему оставляем отдельной: у неё собственный пример и отдельные критерии успеха.

## Охваченное понятие

### Inference Engineering

Работа над эксплуатацией генеративной модели: как выполнять запросы достаточно быстро, экономно и устойчиво для конкретного продукта. При вызове внешнего API часть инфраструктуры контролирует провайдер; при самостоятельном развёртывании больше ответственности за вычислительные ресурсы лежит на команде.

## Суть своими словами

Корректный ответ за минуту может не подходить для интерактивного помощника, а быстрый ответ с неверным содержанием тоже бесполезен. Поэтому оценивают и качество, и условия обслуживания. Сначала находят, где тратится время или память, затем проверяют конкретное изменение под реальной формой нагрузки.

## Как работает

### Путь одного запроса

1. Запрос проходит подготовку: сбор контекста, проверки и передачу на сервер. Время внешнего поиска тоже влияет на ожидание пользователя.
2. При нехватке свободных ресурсов он ждёт в очереди. Очередь может быть причиной медленного ответа даже при быстрой генерации.
3. Во время **prefill** обрабатывают входные токены и подготавливают внутреннее состояние для продолжения.
4. Во время **decode** модель последовательно генерирует выходные токены. Для переиспользования промежуточных данных attention применяется **KV cache**, который занимает память; подробнее — [PagedAttention](https://huggingface.co/docs/text-generation-inference/en/conceptual/paged_attention).
5. Результат передают клиенту целиком или потоком. Потоковая передача показывает начало раньше, но сама по себе не доказывает уменьшение времени полного ответа.

Это упрощённая схема генеративного сервера. Детали зависят от архитектуры модели и инфраструктуры.

### Что измеряют

| Показатель | Что он помогает понять |
| --- | --- |
| Time to First Token, TTFT | Как долго ждать начало ответа |
| Время полного запроса | Сколько ждать готовый результат |
| Скорость выдачи токенов | Насколько быстро поступает продолжение |
| Пропускная способность | Сколько работы система выполняет за единицу времени |
| p95 задержки | Порог, в который укладываются 95% измеренных задержек |
| Ошибки и таймауты | Какая часть запросов не обслуживается успешно |
| Стоимость успешной задачи | Сколько стоит получить пригодный результат, включая повторы |

Пример серверных измерений — [документация метрик vLLM](https://docs.vllm.ai/en/latest/design/metrics/). Для разных измерений важно одинаково определить начало и конец: задержка сервера и полное время приложения могут отличаться.

### Какие решения проверяют

Уменьшение ненужного контекста снижает объём входной работы. Ограничение слишком длинного ответа уменьшает выходную работу. Объединение запросов в batch может повысить пропускную способность, но ожидание группы способно ухудшить задержку отдельного запроса. Более экономное представление модели может сократить потребление памяти, но требует проверки качества. Масштабирование помогает, если проблему действительно решают дополнительные ресурсы; оно не исправляет плохой поиск или бесконечные повторы агента.

При самостоятельном размещении задачи могут доходить до оптимизации GPU-операций и CUDA-ядер, настройки сервера и управления мощностями через Kubernetes или другие средства. Это уровни работы, а не список инструментов, которые обязательно нужны каждому проекту.

## Развёрнутый пример: помощник по документации под нагрузкой

Учебный сценарий. Все числа условные, не результаты тестирования модели или рекомендация по ёмкости сервера.

**Цель продукта:** начало ответа не позднее 2 секунд у 95% запросов, полный ответ не позднее 8 секунд при выбранной рабочей нагрузке. Качество проверяют отдельным набором вопросов.

1. Сначала измеряем приложение целиком: поиск, очередь, начало генерации, завершение и ошибки.
2. Допустим, при одиночных запросах ответ укладывается в цель, а при 20 одновременных запросах условный p95 полного ответа равен 14 секундам. Наблюдения показывают рост очереди, а не времени поиска.
3. Сокращаем ненужные дубли документов в контексте, сохраняя основания ответа. Измеряем снова на тех же вопросах и той же нагрузке; проверяем качество, а не только скорость.
4. Если очередь всё ещё велика, испытываем параметры обслуживания и доступную ёмкость. Меняем по одному фактору, иначе неясно, что помогло.
5. Проверяем короткие и длинные запросы, ошибки и стоимость пригодного ответа. Итог признаётся улучшением только по фактическим измерениям; в этом учебном примере итоговые числа не придуманы.

**Вариант сбоя:** включили streaming, первый токен приходит раньше, но полный ответ всё ещё занимает 14 секунд. Пользователь видит прогресс раньше, однако цель полного времени не выполнена. Нужно отдельно смотреть TTFT и завершение, а не объявлять всю проблему решённой.

## Практические сценарии из жизни

Типовые рабочие сценарии, не кейсы конкретных организаций.

**Интерактивный помощник.** Пользователь ждёт ответ в интерфейсе. Нужны профиль длины запросов, ожидаемая одновременная нагрузка и критерий качества. Важны быстрый старт, плавная выдача и предсказуемость медленных случаев; среднее время скрывает часть проблем.

**Ночная обработка документов.** Команда извлекает поля из большого набора файлов к утру. Мгновенный ответ на каждый файл не нужен; важнее обработать весь объём к сроку с контролем ошибок. Можно проверять пакетную обработку и иные настройки обслуживания. Критерии — число корректно обработанных документов, срок и стоимость, а не только TTFT.

## Ограничения и типичные ошибки

### Ограничения

- Память ограничивают не только параметры модели, но и состояние текущих последовательностей. Рост параллелизма и длины запросов способен вызвать нехватку памяти.
- Оптимизация одного показателя может ухудшить другой. Ускорение массовой обработки не обязательно ускоряет отдельный интерактивный запрос.
- У внешнего API команда не управляет всеми серверными механизмами. Полезно сначала оптимизировать доступные части: объём запросов, длину ответов, повторы и выбор модели, не приписывая себе контроль чужой инфраструктуры.

### Ошибки применения

| Ошибка | Симптом и причина | Проверка или исправление |
| --- | --- | --- |
| Измерить только один короткий запрос | При реальной нагрузке появляется очередь | Повторить измерения на характерных длинах и параллелизме |
| Смотреть только среднее | Часть пользователей регулярно ждёт намного дольше | Смотреть распределение и p95 вместе с ошибками |
| Считать streaming общим ускорением | Начало быстрее, завершение прежнее | Измерять оба показателя отдельно |
| Уменьшать ресурсы без проверки качества | Дешевле запрос, но больше непригодных ответов и повторов | Сравнивать стоимость успешно решённой задачи |
| Повторять запросы без ограничений | Нагрузка растёт во время сбоев | Ограничить число повторов, учитывать ошибки и очередь |

### Когда выбрать другой подход

Для редких запросов готовый API может быть проще собственного сервера. Если проблема — неправильные ответы из-за нерелевантного контекста, сначала исправляют retrieval и инструкции: дополнительный GPU не восстановит отсутствующий факт.

## Самостоятельная практика

Для доступного приложения возьми несколько коротких и длинных запросов. Запиши начало, первый видимый фрагмент, завершение, успех или ошибку. Не создавай массовую нагрузку на чужой сервис: начни с последовательных запросов. Критерий успеха — различаешь время первого фрагмента и полный ответ, понимаешь ограниченность маленькой выборки. Нагрузочные эксперименты с параллелизмом проводи в своей среде; надёжный p95 по нескольким запросам оценить нельзя.

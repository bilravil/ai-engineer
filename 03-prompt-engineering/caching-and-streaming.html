Prompt caching и потоковая выдача ответа

Prompt caching и потоковая выдача ответа

23 нояб. 2026 г.время чтения ~7 мин.

← Prompt Engineering · Краткий справочник

Коротко

Prompt caching может повторно использовать вычислительное состояние общего префикса запросов. Ответ при этом генерируется заново: это отличается от кэша готовых ответов приложения. Streaming передаёт события и части ответа до его завершения, улучшая ощущение ожидания. Кэширование и streaming совместимы: один механизм относится к повторной обработке входа, второй — к доставке результата.

Охваченные понятия

Prompt Caching

В современных LLM API под prompt caching обычно понимают повторное использование обработки совпадающей начальной части запроса: например, постоянных инструкций и документов. Это не обязательно сохранение готового ответа, как можно понять из присланного определения.

Конкретные условия совпадения, минимальный размер, срок хранения и тарифы зависят от провайдера. Наличие одинакового по смыслу текста ещё не означает попадание в кэш. Пример механизма и требования к префиксу — официальная документация caching.

Streaming Responses

При streaming приложение получает последовательность событий: части текста, данные вызова инструмента, статусы и завершение. Часть потока не обязана совпадать с целым словом или одним токеном. Для показа пользователю фрагменты можно накапливать, но для машинной обработки нужно учитывать завершение и ошибки — см. документацию streaming.

Суть своими словами

Кэш префикса помогает не выполнять одну и ту же входную работу полностью при каждом подходящем запросе. Он не означает, что модель больше не обрабатывает новую задачу и не генерирует новый выход. Streaming позволяет раньше увидеть начало, но не гарантирует сокращение полного времени ответа и не делает первую часть окончательной.

Как работает

Кэш общего префикса

  1. Выделяют стабильную часть: инструкции, доступные общие документы, примеры или описание инструментов.
  2. Переменные сведения — текущий вопрос, меняющиеся факты и время — размещают так, чтобы не разрушать повторяемую часть без необходимости. Конкретный порядок должен также сохранять качество промпта.
  3. Сервер определяет, есть ли подходящий сохранённый префикс и выполнены ли условия использования.
  4. При попадании использует сохранённое состояние для обработки продолжения; при промахе выполняет необходимую обработку заново.
  5. Генерирует новый ответ и возвращает сведения об использовании. Эффект проверяют по фактическим показателям, а не по одному визуально быстрому запросу.

Кэширование не увеличивает контекстное окно и не делает общую часть «невидимой» для его лимита. Оно также не отменяет актуальность источников и проверку прав.

Кэш ответа — отдельный механизм

Приложение может хранить готовую пару «условия запроса → результат» и вернуть ответ без новой генерации. Тогда ключ должен учитывать пользователя, доступ, версию источников и другие влияющие условия. Нельзя считать prompt caching API таким же механизмом или использовать кэш ответа только по похожему вопросу, если ответы зависят от аккаунта.

Потоковая доставка

  1. Приложение открывает поддерживаемый сервером поток.
  2. Получает события и собирает фрагменты нужного блока, отличая текст от аргументов инструмента и статусов.
  3. Показывает доступное начало ответа, если это уместно для продукта.
  4. Обрабатывает завершение, остановку по лимиту, отмену и сбой. Открытое соединение или HTTP-успех сами по себе не означают готовый полный ответ.
  5. После завершения собирает нужный объект и проверяет его перед дальнейшим использованием.

Раннее прекращение чтения и фактическая отмена генерации — разные вещи; поведение и расчёт использования зависят от сервиса. Нельзя обещать автоматическую экономию только потому, что пользователь закрыл интерфейс.

Развёрнутый пример: два обращения в поддержку

Учебный сценарий Portal. Все объёмы и времена условные, не измерения API.

Общая часть: инструкции, одинаковые доступные правила D1 и D2, примеры — условно 4000 токенов. Переменная часть: факты аккаунта и вопрос — условно 300 токенов. Новые факты проверяются отдельно для каждого обращения.

A4000300Префикс ещё не сохранён: обработка и запись по правилам сервиса
BТе же 4000Другие 300Возможное чтение совпадающего префикса
  1. Первый оператор спрашивает о клиенте с обычным входом. Приложение передаёт общие правила и его разрешённые факты.
  2. Второй вопрос относится к SSO. Общая доступная часть совпадает, но текущие факты другие. Возможное попадание в prefix cache не означает повтор первого ответа: нужен новый ответ по SSO.
  3. Логический вход каждого запроса по учебным числам — 4300 токенов. Для двух запросов это 8600 входных токенов. При идеальном совпадении второго префикса 4000 из них относятся к повторно используемой части, но это не расчёт оплачиваемой суммы: цены записи, чтения и прочие условия зависят от API.
  4. Ответ B передаётся потоком. В условном измерении запрос начинается в 0 секунд, первый видимый фрагмент приходит в 0.8, завершение — в 3.0.
  5. Если тот же готовый ответ отдавать целиком только на завершении, пользователь увидит его позднее, но полное время в этой иллюстрации останется 3.0. Streaming изменил доставку, а не автоматически скорость генерации.
  6. Проверяют попадание в кэш по данным использования, правильность обоих ответов и состояния потока, а не только отзывчивость интерфейса.

Сбой префикса

Если перед постоянными инструкциями каждый раз вставлять новое время или ID, совпадение нужного префикса может нарушиться. Приложение выглядит «с кэшем», но повторного использования нет. Исправление — разобраться, какие блоки участвуют в совпадении у выбранного сервиса, выделить стабильную разрешённую часть и проверить реальные cache-read показатели.

Практические сценарии из жизни

Типовые рабочие ситуации, не подтверждённые внедрения конкретных компаний.

Много запросов по одному руководству. Пользователи задают разные вопросы по стабильному доступному документу. Общая часть подходит для проверки prefix caching; если доступные версии различаются, это нужно сохранить в запросе и политике использования. Измеряют долю попаданий, стоимость пригодного ответа и задержку, не обещая фиксированного процента экономии.

Интерактивный помощник и фоновая обработка. В чате streaming позволяет раньше читать объяснение; при ночной выгрузке структурированных карточек мгновенный показ не нужен. Во втором случае проще обрабатывать завершённые объекты. Критерии различаются: время первого фрагмента и удобство диалога против полноты, валидации и обработки всего набора к сроку.

Ограничения и типичные ошибки

Ограничения

  • Изменение префикса, срока хранения или конфигурации может привести к промаху; кэш не является обещанием постоянной экономии.
  • Первичная запись и чтение могут учитываться по-разному. Без реального профиля запросов нельзя доказать пользу по стоимости.
  • Часть ответа может быть показана до проверки целого. Если продукт требует проверенный машинный результат, нужно отделять предварительное отображение от принятия результата.
  • Частые изменения документа требуют обновлять содержимое и учитывать версию. Цель попадания в кэш не должна заставлять сохранять устаревшие правила.

Когда выбрать другой подход

Если префикс почти всегда разный и запросов мало, caching может не дать заметной пользы. Если нужен один проверенный объект для фонового процесса, non-streaming может быть проще. Если нужно повторно вернуть готовый неизменный результат, это задача кэша приложения с корректным ключом.

Самостоятельная практика

Раздели свой учебный запрос на стабильные и переменные блоки. Найди поле, которое мешает повторному использованию префикса. Затем вручную собери JSON из трёх фрагментов примера и укажи момент, когда можно валидировать весь объект. При доступе к API отдельно измерь первый фрагмент, завершение и cache usage. Критерий успеха — различаешь ощущение скорости, полную задержку и повторное использование входа.

Проверка понимания

  • Различаю prefix cache и кэш готового ответа.
  • Понимаю, почему cached prefix занимает место в контексте.
  • Могу объяснить причину промаха и способ его измерить.
  • Различаю первый фрагмент, завершение и ошибку потока.
  • Могу безопасно собрать структурированный блок перед обработкой.
